| Python 中的列表（List）和元组（Tuple）有什么区别？                   | 数据结构、可变性         | 基础 | 列表是动态的、可变的（Mutable），可以随时添加、修改或删除元素，使用方括号 `[]` 定义。元组是静态的、不可变的（Immutable），一旦创建其内部元素的指向便不能修改，使用圆括号 `()` 定义。由于不可变性，元组在内存占用和迭代速度上略优于列表，且可以作为字典的键（Hashable），而列表不行。                                                                                                                                                                                                             |
| 解释一下 `__init__` 方法和 `self` 参数的作用。                       | 面向对象编程（OOP）      | 基础 | `__init__` 是 Python 类的初始化方法（构造器），在创建类的新实例时会自动调用，用于初始化对象的属性。`self` 代表类的当前实例对象本身，通过 `self` 可以访问和修改该实例的属性和方法。它不是 Python 的关键字，而是一个强约定，必须作为实例方法的第一个参数。                                                                                                                                                                                                                                         |

| 什么是生成器？`yield` 关键字的作用是什么？它与返回列表相比有何优势？ | 迭代器、生成器、内存管理 | 中级 | 生成器是一种特殊的迭代器，通过在函数中使用 `yield` 关键字来返回值。每次调用 `yield` 时，函数会暂停执行并保存当前所有的运行状态（局部变量等），下次迭代时从暂停处继续。**优势**：与一次性计算并返回完整列表相比，生成器采用惰性计算（Lazy Evaluation），每次只在内存中生成一个值，极大地节省了内存空间，非常适合处理海量数据或无限序列。                                                                                                                                                          |
| Python 的全局解释器锁（GIL）是什么？它如何影响多线程程序性能？       | CPython、多线程、并发    | 高级 | GIL 是 CPython 解释器中的一个互斥锁，它保证同一时刻只有一个线程在执行 Python 字节码。**影响**：由于 GIL 的存在，Python 的多线程在 CPU 密集型任务中无法实现真正的并行计算，性能甚至可能不如单线程（因为线程切换开销）。但对于 I/O 密集型任务（如网络请求、文件读写），线程在等待 I/O 时会释放 GIL，因此多线程依然能显著提升性能。要绕过 GIL 限制进行 CPU 密集型计算，通常需要使用多进程（`multiprocessing`）或 C 扩展。                                                                           |
| 简述 Python 中的 Metaclass（元类）以及继承链（MRO）。                | 面向对象高级特性、MRO    | 高级 | **元类**：在 Python 中，类也是对象，而元类就是“创建类的类”（默认是 `type`）。通过自定义元类，可以在类创建时动态修改类的行为、属性或进行注册等操作。**继承链（MRO）**：即方法解析顺序（Method Resolution Order），决定了在多继承情况下调用方法时查找父类的顺序。Python 3 使用 C3 线性化算法来计算 MRO，保证了局部优先和单调性，可以通过 `ClassName.mro()` 或 `ClassName.__mro__` 查看。                                                                                                           |

| 在 async/await 异步编程中，`asyncio.gather()` 和 `asyncio.create_task()` 有何区别与联系？ | 异步并发、Task 管理 | 中级 | `asyncio.create_task()` 用于将一个协程（Coroutine）包装成一个 Task，并立即将其排入事件循环的调度队列中，使其在后台并发运行，返回一个 Task 对象。`asyncio.gather()` 用于并发运行多个可等待对象（Awaitables，如协程或 Task），并等待它们全部完成，返回结果列表。**联系**：通常可以先用 `create_task` 创建多个任务，然后将这些任务传给 `gather` 来等待它们全部执行完毕并收集结果。                                              |
| 解释 asyncio 中事件循环（Event Loop）的核心工作模型。                                     | 事件循环、异步 I/O  | 高级 | 事件循环是 asyncio 的核心，它是一个无限循环，负责管理和调度不同任务的执行、处理网络 I/O 事件和定时器。**工作模型**：它采用单线程协作式多任务模型。当一个协程遇到耗时的 I/O 操作（如 `await asyncio.sleep()` 或网络请求）时，它会主动让出控制权（Yield Control）给事件循环。事件循环随后会去执行其他准备好的协程。当底层的 I/O 操作完成时（通过 epoll/kqueue 等系统调用监听），事件循环会在未来的某个循环中恢复该协程的执行。 |

## FastAPI 框架

| 问题                                                                    | 考察范围               | 等级 | 参考答案                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------------------------- | ---------------------- | ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 在 FastAPI 中，`async def` 路由与 `def` 路由的内部执行机制有何区别？    | FastAPI、并发模型      | 中级 | 当使用 `async def` 定义路由时，FastAPI 会直接在主事件循环（Event Loop）中以协程的方式运行它。如果里面有阻塞的同步代码（如 `time.sleep`），会阻塞整个服务器。当使用普通的 `def` 定义路由时，FastAPI 会将其放入一个外部的线程池（Threadpool）中运行，以避免阻塞主事件循环。因此，如果是异步 I/O 操作应使用 `async def`，如果是同步的阻塞操作（如传统的同步数据库查询）应使用 `def`。                                                            |
| 解释 FastAPI 的依赖注入系统是如何递归解析的？                           | 依赖注入（DI）         | 高级 | FastAPI 的依赖注入系统（`Depends`）允许在路由处理函数中声明所需的依赖项。**递归解析**：当一个路由依赖了 A，而 A 又依赖了 B 和 C 时，FastAPI 会在请求到达时，自动构建依赖图（Dependency Graph）。它会先解析并执行最底层的依赖（B 和 C），将其结果传递给 A，最后将 A 的结果传递给路由函数。它还支持缓存（`use_cache=True`），在同一个请求中多次请求同一个依赖只会执行一次。                                                                     |
| 如何在 FastAPI 中安全地管理异步数据库连接？                             | 数据库连接池、生命周期 | 中级 | 通常通过 FastAPI 的生命周期事件（Lifespan Events）或依赖注入来安全管理。**Lifespan 方式**：使用 `@asynccontextmanager` 定义 lifespan 函数，在应用启动时初始化异步数据库连接池（如 asyncpg、SQLAlchemy async engine），在应用关闭时优雅地关闭连接池。**依赖注入方式**：编写一个生成器依赖函数（使用 `yield`），在请求开始时从连接池获取一个 Session，通过 `yield session` 提供给路由，在路由执行完毕后（`finally` 块中）安全地关闭或归还连接。 |
| 在 FastAPI 中，如何处理请求的全局横切关注点（如日志、CORS、请求计时）？ | 中间件（Middleware）   | 基础 | 在 FastAPI 中，处理全局横切关注点通常使用**中间件（Middleware）**。可以通过 `@app.middleware("http")` 装饰器编写自定义中间件，它会在请求到达路由之前拦截请求（如记录开始时间），然后调用 `call_next(request)` 将请求传递给后续路由，最后在响应返回前再次拦截（如计算耗时、添加自定义 Header、记录日志）。对于 CORS，FastAPI 提供了内置的 `CORSMiddleware`，只需通过 `app.add_middleware()` 挂载并配置允许的源、方法和请求头即可。             |

| `uv` 与传统的 `pip + virtualenv` 或 `poetry` 相比，有哪些核心优势？               | 包管理工具、uv     | 中级 | `uv` 是一个由 Rust 编写的极速 Python 包解析器和安装器。**核心优势**：1. **极致的速度**：比 pip 和 poetry 快几十倍，极大地减少了 CI/CD 和本地环境构建的时间。2. **统一的工具链**：它不仅能替代 pip 进行包安装，还能替代 virtualenv 创建虚拟环境，甚至替代 pip-tools 进行依赖锁定。3. **全局缓存**：支持全局包缓存，不同项目依赖同一个版本的包时无需重复下载和占用磁盘空间。4. **兼容性**：无缝兼容现有的 `requirements.txt` 和 `pyproject.toml` 标准。 |
| 解释 `uv.lock` 文件的作用，它和 `pyproject.toml` 以及 `pip freeze` 的区别是什么？ | 依赖锁定、版本管理 | 中级 | `uv.lock` 是 uv 生成的跨平台依赖锁定文件，记录了项目中所有直接和间接依赖的精确版本及哈希值，确保在任何机器上都能进行确定性安装（Deterministic Build）。**区别**：`pyproject.toml` 是声明式的配置文件，通常只定义依赖的宽泛范围（如 `requests >= 2.0`）；`pip freeze` 输出的是当前环境中已安装的所有包的具体版本，但它无法区分哪些是直接依赖、哪些是子依赖，且跨平台兼容性差；`uv.lock` 结合了两者的优点，既能锁定精确版本树，又能跨平台保证一致性。   |

| 当浏览器里面输入网址，发生了哪些事情                                                           | 网络协议、浏览器渲染原理、DNS 解析、TCP/IP。 | 中级 | 1. **URL 解析**：浏览器解析输入的 URL，确定协议、域名、路径等。 2. **DNS 解析**：浏览器查找本地缓存、系统缓存等，若无则向 DNS 服务器查询，将域名解析为 IP 地址。 3. **建立 TCP 连接**：浏览器与服务器通过“三次握手”建立 TCP 连接（若是 HTTPS 则还需进行 TLS 握手）。 4. **发送 HTTP 请求**：浏览器向服务器发送 HTTP 请求报文。 5. **服务器响应**：服务器处理请求并返回 HTTP 响应报文（包含 HTML 数据等）。 6. **浏览器渲染页面**： - 解析 HTML 构建 DOM 树。 - 解析 CSS 构建 CSSOM 树。 - 合并 DOM 树和 CSSOM 树生成渲染树（Render Tree）。 - 布局（Layout）：计算各节点在屏幕上的确切位置和大小。 - 绘制（Paint）：将页面像素绘制到屏幕上。 7. **断开连接**：数据传输完毕后，通过“四次挥手”断开 TCP 连接（若开启 keep-alive 则保持连接）。 |

| 在构建 Docker 镜像时，为什么建议将 `COPY package.json` 和 `npm install` 放在 `COPY . .` 之前？ | Docker 构建优化、镜像分层缓存                | 加分 | 这是为了充分利用 Docker 的**分层缓存机制**。Docker 构建时每条指令生成一层，若文件无变化则复用缓存。业务代码（`COPY . .`）变动频繁，而依赖（`package.json`）变动较少。如果先拷贝所有代码，任何修改都会导致后续的 `npm install` 缓存失效，每次都要重新下载依赖。先拷贝 `package.json` 并安装依赖，只要依赖没变就能直接复用 `node_modules` 缓存，极大提升构建速度。                                                                                                                                                                                                                                                                                                                                                                            |

| SQL 中的 `LEFT JOIN` 和 `INNER JOIN` 的区别是什么？                                            | 数据库、SQL                                  | 加分 | **INNER JOIN（内连接）**：取交集，只返回两个表中**匹配成功**的行。如果左表的数据在右表中无匹配，则直接丢弃。 **LEFT JOIN（左连接）**：以左表为基准，返回**左表的所有行**。即使右表中没有匹配的记录，左表的数据也会被保留，此时右表对应的字段会用 `NULL` 填充。                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

| Docker 容器和传统虚拟机（VM）有什么本质区别？                                                  | 容器化、Docker                               | 基础 | 传统虚拟机通过 Hypervisor 在物理服务器上虚拟出完整的硬件，并运行完整的客户操作系统（Guest OS），资源占用大、启动慢（分钟级）。Docker 容器则是基于宿主机操作系统的轻量级虚拟化，它利用 Linux 的 Namespace 实现隔离，利用 Cgroups 实现资源限制。多个容器共享宿主机的操作系统内核，没有 Guest OS 的开销，因此启动极快（秒级），资源利用率极高。                                                                                                                                                                                                                                                                                                                                                                                                |
| Kubernetes（K8s）中的 Pod 是什么？为什么 K8s 的最小调度单元是 Pod 而不是容器？                 | Kubernetes 基础                              | 中级 | **Pod** 是 K8s 中创建和管理的最小、最基本的可部署计算单元。一个 Pod 可以包含一个或多个紧密相关的容器，这些容器共享同一个网络命名空间（IP 和端口）和存储卷（Volume）。**为什么是 Pod**：在实际业务中，经常会有多个进程/容器需要紧密协作（如主应用容器和负责收集日志的 Sidecar 容器）。如果以容器为调度单元，很难保证它们被调度到同一台机器上并共享网络和存储。Pod 提供了一个抽象层，将这些“亲密”的容器打包在一起，作为一个整体进行调度和管理。                                                                                                                                                                                                                                                                                               |
