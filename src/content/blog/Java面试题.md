## Java 基础与进阶

| 面向对象的三大特性是什么？请结合 Java 简述。 | 面向对象基础 | 基础 | 封装、继承、多态。**封装**是隐藏对象的属性和实现细节，仅对外提供公共访问方式；**继承**是子类继承父类的特征和行为，实现代码复用；**多态**是同一个行为具有多个不同表现形式或形态的能力（通过重写和接口实现），在运行时动态绑定。 |
| `String`、`StringBuilder` 和 `StringBuffer` 的区别是什么？ | Java 核心类、线程安全 | 基础 | `String` 是不可变类，每次修改都会生成新的对象，性能较差；`StringBuilder` 是可变类，非线程安全，但在单线程下性能最好；`StringBuffer` 也是可变类，内部方法被 `synchronized` 修饰，是线程安全的，但性能略低于 `StringBuilder`。 |
| `HashMap` 的底层实现原理是什么？在 JDK 1.8 中做了哪些优化？ | 集合框架、数据结构 | 中级 | `HashMap` 底层基于**数组+链表/红黑树**实现。通过对 key 进行 hash 计算得出数组索引。在 JDK 1.8 中，当链表长度大于 8 且数组长度大于 64 时，链表会转化为红黑树，以将查询时间复杂度从 O(n) 降低到 O(log n)。同时，1.8 将头插法改为了尾插法，避免了并发扩容时出现死循环的问题。 |
| 什么是反射？在实际开发中有哪些应用场景？ | Java 反射机制 | 中级 | 反射是指在运行状态中，对于任意一个类，都能够知道这个类的所有属性和方法；对于任意一个对象，都能够调用它的任意方法和属性。**应用场景**：Spring 的 IoC 容器（通过反射创建 Bean）、AOP 动态代理（JDK 动态代理）、JDBC 数据库连接加载驱动、各种框架的注解解析等。 |

## JVM 与并发编程

| 问题 | 考察范围 | 等级 | 参考答案 |
| --- | --- | --- | --- |
| 简述 Java 中的线程池核心参数及工作流程。 | 并发编程、线程池 | 基础 | 核心参数：`corePoolSize`（核心线程数）、`maximumPoolSize`（最大线程数）、`keepAliveTime`（空闲存活时间）、`workQueue`（阻塞队列）、`handler`（拒绝策略）。**工作流程**：新任务提交时，若当前线程数小于核心，则创建新线程；若达到核心，则放入队列；若队列已满且未达到最大线程数，则创建非核心线程；若达到最大线程数，则执行拒绝策略。 |
| 什么是 `ThreadLocal`？它存在什么隐患，如何解决？ | 并发编程、内存泄漏 | 中级 | `ThreadLocal` 提供线程局部变量，保证每个线程都有自己独立的变量副本，避免并发冲突。**隐患**：`ThreadLocalMap` 的 key 是弱引用，而 value 是强引用，若 `ThreadLocal` 外部没有强引用被回收，key 会变为 null，但 value 依然存在，导致内存泄漏。**解决办法**：每次使用完 `ThreadLocal` 后，显式调用 `remove()` 方法清理。 |
| 简述 JVM 的内存模型（JMM）以及垃圾回收（GC）的常见算法。 | JVM、垃圾回收 | 高级 | **JMM** 规定了所有变量存储在主内存，每个线程有自己的工作内存，线程对变量的操作必须在工作内存中进行，通过 `volatile` 等关键字保证可见性和有序性。**常见 GC 算法**：标记-清除（产生内存碎片）、复制算法（适合新生代，存活率低）、标记-整理（适合老年代，存活率高）。现代垃圾收集器如 G1 采用化整为零的 Region 划分，结合了复制和标记-整理算法，可预测停顿时间。 |
| 线上系统突然频繁发生 OOM（Out Of Memory），你会如何排查？ | JVM 调优、线上排错 | 高级 | 1. **保留现场**：确保启动参数配置了 `-XX:+HeapDumpOnOutOfMemoryError`，拿到 OOM 时的 Heap Dump 内存快照文件。2. **日志分析**：查看应用日志和 GC 日志，确认是堆内存溢出、元空间溢出还是直接内存溢出。3. **快照分析**：使用 MAT (Memory Analyzer Tool) 或 JProfiler 打开 Dump 文件，查看大对象（Dominator Tree），找到占用内存最多的类和其实例。4. **定位代码**：根据大对象的 GC Roots 引用链，定位到具体的业务代码，排查是否是死循环、集合未清理或一次性查询数据量过大导致。 |

## Spring 与 Spring Boot

| 问题 | 考察范围 | 等级 | 参考答案 |
| --- | --- | --- | --- |
| 什么是 Spring 的 IoC 和 AOP？ | Spring 核心概念 | 基础 | **IoC（控制反转）**是将对象的创建和依赖关系管理交由 Spring 容器负责，降低组件之间的耦合度（通常通过依赖注入 DI 实现）。**AOP（面向切面编程）**是在不修改原有业务代码的情况下，通过代理模式将横切关注点（如日志、事务、权限校验）动态织入到业务逻辑中。 |
| Spring Boot 的自动配置原理是什么？ | Spring Boot 源码 | 中级 | 核心在于 `@SpringBootApplication` 注解，它包含了 `@EnableAutoConfiguration`。该注解通过 `SpringFactoriesLoader` 扫描所有 jar 包下 `META-INF/spring.factories`（或 Spring Boot 2.7+ 的 `AutoConfiguration.imports`）文件，加载配置类。结合 `@Conditional` 系列注解（如 `@ConditionalOnClass`、`@ConditionalOnMissingBean`），在满足特定条件时自动将 Bean 注入到 Spring 容器中。 |
| Spring 是如何解决循环依赖的？ | Spring 源码、生命周期 | 高级 | Spring 通过**“三级缓存”**解决单例模式下的属性注入循环依赖。第一级缓存存放完全初始化好的 Bean；第二级缓存存放早期暴露的 Bean（已实例化但未填充属性）；第三级缓存存放 Bean 工厂（用于生成代理对象）。当 A 依赖 B，B 依赖 A 时，A 实例化后将 ObjectFactory 放入三级缓存，B 注入 A 时通过三级缓存获取 A 的早期引用（若有 AOP 则生成代理对象并放入二级缓存），从而打破死循环。注意：构造器注入的循环依赖 Spring 无法解决。 |

## 数据库 (PostgreSQL & Redis)

| 问题 | 考察范围 | 等级 | 参考答案 |
| --- | --- | --- | --- |
| 简述 PostgreSQL 的默认事务隔离级别，以及它与 MySQL 的一个核心区别。 | 数据库基础、事务 | 基础 | **默认隔离级别**：PostgreSQL 的默认隔离级别是读已提交（Read Committed），而 MySQL InnoDB 默认是可重复读（Repeatable Read）。**核心区别**：PostgreSQL 是功能强大的对象关系型数据库，原生支持丰富的复杂数据类型（如 JSONB、数组）和强大的扩展（如 PostGIS）；而 MySQL 早期更偏向于轻量级的纯关系型存储。 |
| 什么是 MVCC？PostgreSQL 是如何通过 MVCC 实现并发控制的？ | 数据库底层、并发控制 | 中级 | **MVCC（多版本并发控制）**使得读写操作互不阻塞。**PostgreSQL 实现**：每次更新或删除数据时，PG 不会立即覆盖原数据，而是插入新版本数据，并将旧版本标记为过期（通过隐藏字段 `xmin` 和 `xmax` 记录事务 ID）。不同事务根据自己的快照（Snapshot）决定能看到哪个版本的数据，从而实现隔离。 |
| 简述 PostgreSQL 中的 VACUUM 机制。为什么会出现表膨胀（Table Bloat），如何解决？ | 数据库运维、底层机制 | 高级 | **VACUUM 机制**用于回收被标记为删除或更新的旧版本数据（Dead Tuples）占用的物理空间。**表膨胀原因**：由于 PG 的 MVCC 机制，频繁的 UPDATE/DELETE 会产生大量死元组，若 AutoVacuum 运行不及时或被长事务阻塞，死元组无法回收，导致表文件体积不断增大。**解决办法**：合理配置 `autovacuum`，避免长事务，必要时手动执行 `VACUUM` 或使用 `pg_repack` 插件重组空间。 |
| SQL 中的 `LEFT JOIN` 和 `INNER JOIN` 的区别是什么？ | 数据库、SQL | 加分 | **INNER JOIN（内连接）**：取交集，只返回两个表中**匹配成功**的行。如果左表的数据在右表中无匹配，则直接丢弃。 **LEFT JOIN（左连接）**：以左表为基准，返回**左表的所有行**。即使右表中没有匹配的记录，左表的数据也会被保留，此时右表对应的字段会用 `NULL` 填充。 |
| 什么是 Redis 的缓存穿透、缓存击穿和缓存雪崩？如何解决？ | Redis、高并发架构 | 高级 | **缓存穿透**指查询不存在的数据，请求直接打到数据库。解决：缓存空值或使用布隆过滤器。**缓存击穿**指某个热点 Key 过期瞬间，大量并发请求打到数据库。解决：加互斥锁（如 Redisson 分布式锁）或设置热点 Key 逻辑上永不过期。**缓存雪崩**指大量 Key 在同一时间集中过期，或 Redis 宕机。解决：Key 的过期时间加上随机值，搭建 Redis 高可用集群（哨兵或 Cluster），以及服务降级/限流。 |

## Docker 与 Kubernetes

| 问题 | 考察范围 | 等级 | 参考答案 |
| --- | --- | --- | --- |
| Docker 容器和传统虚拟机（VM）有什么本质区别？ | 容器化、Docker | 基础 | 传统虚拟机通过 Hypervisor 在物理服务器上虚拟出完整的硬件，并运行完整的客户操作系统（Guest OS），资源占用大、启动慢。Docker 容器则是基于宿主机操作系统的轻量级虚拟化，利用 Linux 的 Namespace 实现隔离，利用 Cgroups 实现资源限制。多个容器共享宿主机的操作系统内核，没有 Guest OS 的开销，启动极快，资源利用率极高。 |
| Kubernetes（K8s）中的 Pod 是什么？为什么 K8s 的最小调度单元是 Pod 而不是容器？ | Kubernetes 基础 | 中级 | **Pod** 是 K8s 中创建和管理的最小可部署计算单元。一个 Pod 可以包含一个或多个紧密相关的容器，共享网络命名空间和存储卷。**原因**：实际业务中常有多个进程/容器需紧密协作（如主应用和日志收集 Sidecar）。若以容器为调度单元，很难保证它们被调度到同一台机器并共享网络和存储。Pod 提供了抽象层，将这些“亲密”容器打包作为一个整体调度。 |
| 在 Kubernetes 中，Service 的作用是什么？常见的 Service 类型有哪些？ | K8s 网络、Service | 高级 | **作用**：Pod 的 IP 是动态的，Service 为一组提供相同功能的 Pod 提供统一、固定的访问入口（IP 和 DNS 名），并实现负载均衡。**常见类型**：1. ClusterIP（默认，仅集群内访问）；2. NodePort（在每个 Node 开放静态端口，外部通过 NodeIP:NodePort 访问）；3. LoadBalancer（结合云厂商负载均衡器暴露到公网）；4. ExternalName（映射到外部 DNS 域名）。 |

## 中间件与系统架构

| 问题 | 考察范围 | 等级 | 参考答案 |
| --- | --- | --- | --- |
| Kafka 的核心架构组件有哪些？它是如何保证高吞吐量的？ | 消息队列、Kafka | 中级 | **核心组件**：Producer（生产者）、Consumer（消费者）、Broker（节点）、Topic（主题）、Partition（分区）、Zookeeper/KRaft（元数据管理）。**高吞吐量原因**：1. **顺序写磁盘**：利用磁盘顺序写速度远高于随机写的特性；2. **零拷贝（Zero-Copy）**：使用 `sendfile` 系统调用，数据直接从内核缓冲区发送到网卡，避免了用户态与内核态的切换和数据拷贝；3. **批量发送与压缩**：生产者批量发送消息并支持压缩（如 Snappy/LZ4）。 |
| 什么是 Kafka 的消费者组（Consumer Group）？一个 Partition 能被同一个组内的多个消费者消费吗？ | 消息队列、并发消费 | 中级 | **消费者组**是 Kafka 实现发布-订阅模型和队列模型的核心机制。组内的所有消费者共同消费一个 Topic 的数据，每条消息只会被组内的一个消费者处理。**不能**。Kafka 规定，一个 Partition 在同一时刻只能被同一个消费者组内的一个消费者消费。这是为了保证 Partition 内部消息的顺序消费。如果组内消费者数量大于 Partition 数量，多出的消费者将处于空闲状态。 |
| Kafka 是如何保证消息不丢失的（高可用与可靠性）？ | 分布式理论、Kafka | 高级 | 1. **生产者端**：设置 `acks=all`（或 `-1`），确保消息被 Leader 写入并同步到所有 ISR（In-Sync Replicas）副本后才返回成功，同时配置重试机制。2. **Broker 端**：通过多副本机制（Replication），每个 Partition 有一个 Leader 和多个 Follower。Leader 宕机时，从 ISR 中选举新 Leader。3. **消费者端**：关闭自动提交位移（`enable.auto.commit=false`），在业务逻辑处理成功后再手动提交 Offset，防止消息被拉取但未处理完就宕机导致丢失。 |
| 在 Kafka 中，如果某条消息处理失败或耗时过长，如何避免它阻塞整个 Partition 的消费？ | 消息队列、异常处理 | 高级 | Kafka 的 Partition 是严格顺序消费的，如果单条消息卡住，会阻塞后续消息。**解决方案**：引入**死信队列（Dead Letter Queue, DLQ）**和**重试队列**机制。消费者在处理消息失败或超时时，不应无限重试或卡死，而是将该消息捕获并发送到一个专门的“重试 Topic”。如果重试多次仍失败，则将其发送到“死信 Topic”进行持久化，等待人工介入排查。主消费者在转发异常消息后，直接提交 Offset 并继续消费下一条消息，从而保证主流程的畅通。 |
| 当浏览器里面输入网址，发生了哪些事情？ | 网络协议、浏览器渲染 | 中级 | 1. URL 解析；2. DNS 解析（将域名解析为 IP）；3. 建立 TCP 连接（三次握手，HTTPS 需 TLS 握手）；4. 发送 HTTP 请求；5. 服务器处理并返回 HTTP 响应；6. 浏览器渲染页面（解析 HTML 构建 DOM 树，解析 CSS 构建 CSSOM 树，合并为 Render Tree，布局并绘制）；7. 断开连接（四次挥手，或 keep-alive 保持）。 |
| 简述分布式系统中的 CAP 定理，以及在实际架构中如何取舍？ | 分布式理论、架构设计 | 高级 | **CAP 定理**指分布式系统无法同时满足一致性（Consistency）、可用性（Availability）和分区容错性（Partition tolerance），最多只能同时满足两项。由于网络分区（P）是客观存在的，实际架构中通常在 CP 和 AP 之间取舍。金融/支付系统通常选择 CP，保证数据强一致性；而电商/社交系统通常选择 AP，保证高可用性，并通过最终一致性（如消息队列、补偿机制）来弥补数据短暂的不一致。 |
| 什么是分布式锁？在 Java 中通常如何实现？ | 分布式架构、并发控制 | 高级 | 分布式锁是控制分布式系统之间同步访问共享资源的一种方式。**常见实现**：1. **基于数据库**：利用唯一索引或排他锁（`FOR UPDATE`），性能较差。2. **基于 Redis**：使用 `SETNX` 命令，配合 Lua 脚本保证原子性，或者直接使用成熟的框架如 Redisson（内置看门狗机制解决锁续期问题）。3. **基于 ZooKeeper**：利用临时顺序节点和 Watcher 机制实现，可靠性高，但性能略低于 Redis。 |
| Session、Cookie、JWT 分别是什么？它们的关系与区别？ | 身份认证、网络安全 | 加分 | **Cookie** 是浏览器存储在本地的文本数据，请求时会自动携带。**Session** 是服务端认证机制，服务端保存用户状态，将 `Session ID` 存入客户端 Cookie 中，缺点是占用服务端内存，不利于分布式。**JWT** 是无状态的 Token 认证方案，服务端不存状态，只负责签发和校验 Token（通常存放在 LocalStorage 或请求头中），适合分布式架构，但缺点是 Token 签发后在过期前难以主动撤销。 |
| 什么是 OAuth 2.0？简述其最常用的授权码模式（Authorization Code）流程。 | 身份认证、第三方授权 | 加分 | **OAuth 2.0** 是一个行业标准的**授权协议**，允许用户授权第三方应用访问其资源，而无需暴露账号密码（如“微信/GitHub 登录”）。 **授权码模式流程**：1. 第三方应用引导用户跳转到授权服务器；2. 用户同意授权后，服务器重定向回第三方应用并附带一个**授权码（Code）**；3. 第三方应用在**后端**使用该 Code 向授权服务器换取 **Access Token**；4. 第三方应用携带 Token 访问资源服务器获取用户数据。 |
